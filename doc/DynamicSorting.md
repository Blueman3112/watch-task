# 动态紧迫度排序机制 (Dynamic Urgency Sorting)

为了确保双端（手表与手机）始终能将最核心、最紧急的任务推送到用户的视线中心，本应用摒弃了传统的静态列表排序，采用了一套基于**“优先级 + 距离截止时间”**的**动态紧迫度算法 (Dynamic Urgency Score)**。

## 1. 宏观排序顺位

系统对任务的整体排序遵循以下三个递进的原则：

1. **唯一王座（Top/Pin）**：具有绝对的最高优先级。系统内永远只允许存在唯一一个被 Top 置顶的任务，它无视任何时间和紧迫度设定，强制霸占中心。
2. **动态紧迫度得分（Urgency Score）**：在没有置顶任务，或者非置顶任务之间，系统会根据每个任务实时计算出的紧迫度得分进行降序排列（得分越高越靠前）。
3. **创建时间（Fallback）**：如果多个任务的动态紧迫度得分完全一致，则按照创建时间降序排列（越新创建的排在越前面）。

---

## 2. 动态紧迫度得分算法 (核心)

任务的最终得分计算公式为：
**`最终得分 (Urgency Score) = 基础优先级分 (Base Score) + 时间附加分 (Time Factor)`**

### 2.1 基础优先级分 (Base Score)
根据用户在创建任务时选择的属性，赋予一个固定的底分：
*   🔴 **Emergency (紧急)**： `+300 分`
*   🟡 **Important (重要)**： `+200 分`
*   🟢 **Regular (普通)**： `+100 分`
*   ⚪ **Long_term (长远)**： `+0 分`

### 2.2 时间附加分 (Time Factor)
系统会获取当前时间（`Now`），并与任务设定的截止时间（`Due Date`）进行对比，得出剩余时间（`TimeLeftHours`）。然后根据剩余时间的不同区间赋予动态加分：

*   **未设置截止时间的任务**：时间附加分永远为 `0`。
*   **大于 72 小时 (3天以上)**：说明时间还非常充裕，时间附加分为 `0`。
*   **进入 72 小时倒计时 (0 ~ 72小时)**：
    *   **线性飙升机制**：分数会随着时间的流逝线性增加。倒数 72 小时时分数为 0，无限逼近 0 小时时分数为极限的 `400` 分。
    *   公式：`((72 - 剩余小时数) * (400 / 72))`
*   **已逾期 (剩余时间 < 0 小时)**：
    *   **超级惩罚机制**：一旦任务过期，立刻赋予一笔高达 `500` 分的基础逾期附加分，并且每逾期 1 小时再额外加 `10` 分。
    *   公式：`500 + (逾期小时数 * 10)`

---

## 3. 算法引发的场景效应 (举例)

*   **普通任务熬成“Boss”**：一个原本是 Regular（基础 100分）的任务，只要它即将过期（时间附加分接近 400分），它的总分会逼近 500分。此时它的顺位会超越一个刚刚新建的、距离截止还有 4 天的 Emergency（总分 300分）任务。这就是**“后来居上”**。
*   **红晕压迫（系统锁定）**：根据 UI 逻辑，当排在最中心的任务其总分突破 **`500 分`** 时，手表端边缘会闪烁强烈的红色光晕 (`isSystemLocked`)。这通常意味着有任务**已逾期**，或者**高优先级任务进入了最后极速倒计时**（如 Emergency 任务进入最后 36 小时）。

---

## 4. 刷新与重算机制

因为时间是在不断流逝的，每个任务的“时间附加分”也是在不断变化的，所以系统需要定期重新洗牌：

*   **自动轮询刷新频率：`1 分钟 (60,000 ms)`**
*   **实现方式**：在手机端和手表端的 `ViewModel` 中，均通过挂起函数维护了一个 `tickerFlow`（心跳流）。系统每隔恰好 60 秒会发射一次最新的时间戳 `System.currentTimeMillis()`。
*   **无缝重排**：底层数据库每次监听到这个时间戳更新，就会立刻将所有的任务丢进 `TaskSorter` 中，使用这个最新的时间戳重算一遍每个任务的分数并完成列表重排。这一切在后台悄无声息地进行，用户会看到原本排在后面的任务随着时间的推移，在没有人工干预的情况下一点点往雷达中心“蠕动”。
